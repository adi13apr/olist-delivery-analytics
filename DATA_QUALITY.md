## Required checks

| Check | Description | Count | Unit | Decision |
|---|---|---|---|---|
| `01_duplicate_order_id` | order_id is unique in orders | 0 | order_ids | Every row sharing a duplicated order_id is kept in stg_orders and excluded from delivery metrics with reason `duplicate_order_id`, since there is no rule for picking the right copy. |
| `02_orphan_order_items` | order_items with no matching order | 0 | item rows | Kept in stg_order_items with `has_matching_order = false`; excluded from any analysis that joins items to orders. |
| `03_delivered_missing_delivery_date` | Delivered orders missing a delivery date | 8 | orders | Kept in stg_orders and excluded from delivery metrics with reason `missing_delivered_date`; still counted in order volumes. |
| `04_delivery_before_purchase` | Delivery before purchase | 0 | orders | Excluded from delivery metrics with reason `delivered_before_purchase` (a negative delivery time is impossible, so one of the timestamps is wrong). |
| `05_multiple_reviews_per_order` | Multiple reviews per order | 547 | orders | All reviews are kept in stg_reviews. Order-level analysis uses the latest review (`is_latest_for_order`: latest answer timestamp, then latest creation date). |

## Other findings

Issues found while profiling the data that the brief did not list.

| Check | Description | Count | Unit | Decision |
|---|---|---|---|---|
| `06_review_id_reused` | review_id shared by several orders | 789 | review_ids | review_id is not a key in this dataset. (review_id, order_id) is unique and is used as the key; stg_reviews carries `orders_for_review_id`. |
| `07_orders_without_review` | Orders with no review | 768 | orders | Kept. Review metrics are computed over reviewed orders only; a missing review is never treated as a score. |
| `08_carrier_before_purchase` | Carrier handoff before purchase | 166 | orders | Kept and still eligible for delivery metrics, which use only the purchase, delivered and estimated dates. The carrier date is unreliable for these orders, so they must be excluded from any future carrier-leg metric. |
| `09_customer_before_carrier` | Delivered to customer before carrier pickup | 23 | orders | Kept and still eligible for delivery metrics (purchase-to-delivery is consistent). Same caveat as above for carrier-leg metrics. |
| `10_undelivered_with_delivery_date` | Non-delivered status with a delivery date | 6 | orders | order_status is treated as the source of truth: these orders are excluded from delivery metrics with reason `status_not_delivered`. |
| `11_orders_without_payment` | Orders with no payment | 1 | orders | Kept. Not used by delivery metrics; payment analysis will report it as unpaid. |
| `12_zero_value_payments` | Payments with value <= 0 | 9 | payment rows | Kept as recorded (vouchers and undefined payments). Not used by delivery metrics. |
| `13_undefined_payment_type` | payment_type = 'not_defined' | 3 | payment rows | Kept as recorded. Not used by delivery metrics. |
| `14_products_missing_category` | Products with no category | 610 | products | Kept; stg_products labels them `uncategorized`. |
| `15_categories_missing_translation` | Categories with no English translation | 2 | categories | Kept; stg_products falls back to the Portuguese category name. |

## Delivery metric exclusions

Delivery metrics (`delivery_days`, `estimated_days`, `is_late` in `stg_orders`) use only delivered orders with valid dates. Every other order stays in `stg_orders` with exactly one `exclusion_reason`; the first matching rule below wins.
